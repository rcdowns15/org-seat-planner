# Org Seat Planner — repo guide for every agent

A portfolio demo where engineering leaders at a fictional company, **Second Republic Bank**, edit
org and seat data in a write-back app (move people between squads, with validation, audit history
and conflict handling). A pipeline ingests mock biweekly Workday reports, dbt models the data and
reconciles HRIS facts against the leaders' plan, and (later) a semantic layer defines consistent
headcount metrics. All data is mock, generated by a seeded script. Rob is building it to show, in a
hiring-manager interview, that he can own a people-data write-back tool end to end, and he must be
able to explain every line. **Prefer clear, conventional code over clever code.**

## How work is organized
- `docs/MASTER_PLAN.md`: goal, portfolio-ready cut line, big rocks (BR), sequencing, review checkpoints, status rollup. Source of truth for priorities.
- `docs/specs/BR-XX-*.md`: one spec per big rock. Each contains its little rocks (LR) as issues with acceptance criteria. New specs and little rocks start from `docs/templates/`.
- `docs/PROGRESS.md`: "Where we stand" state block plus a dated log of what moved. Navigator owns it; the orchestrator adds one line per completed little rock.
- `docs/DECISIONS.md`: architecture and scope decisions with the why. Navigator owns it.
- `docs/PARKING_LOT.md`: good ideas that aren't in the plan. Navigator triages Rob's new ideas into a spec, the parking lot, or nowhere.

Little rock IDs look like `LR-02-03` (big rock 02, little rock 03); big rocks are `BR-02`. Reference them in branch names, commits, and PR titles.

## Agent roles
| Role | Runs as | Talks to | Does |
|---|---|---|---|
| navigator | Main session (`claude --agent navigator`) | Rob, orchestrator (through Rob) | Thinks with Rob, level-sets progress vs. goals, edits `docs/`, hands ready work to the orchestrator as a written brief that Rob pastes in. Writes no product code. |
| orchestrator | Top-level session (`claude --agent orchestrator`) | Rob (who relays the navigator's briefs and reports), executors, reviewer | Turns issues into a dispatch plan, spawns executors, verifies results, has them reviewed, opens PRs for Rob, updates issue status. |
| executor | Subagent spawned by orchestrator or Rob (`@agent-executor`) | whoever spawned it | Implements exactly one little rock in an isolated worktree, tests it, commits, reports. |
| reviewer | Subagent spawned by orchestrator | orchestrator | Read-only, independent review: every little rock before its PR opens, and each big rock once its little rocks are merged. Ranks findings P1 (blocks) / P2 (fix or waive) / P3 (note). |

## Models
Pinned so behavior doesn't drift between sessions; upgrade on purpose and log it in `docs/DECISIONS.md`.
- Main sessions (including gstack reviews): `claude-opus-5-5`, the default in `.claude/settings.json`.
- navigator, orchestrator and reviewer: `claude-opus-5-5`. executor: `claude-sonnet-5-5` by default. A little rock whose header says `executor model: opus` gets an Opus executor.
- Codex outside voice for gstack reviews: `gpt-6-luna` (`GSTACK_CODEX_MODEL` in `.claude/settings.json`). Pipe the prompt on stdin (`codex exec -`).

## Checkpoints and state
The "Where we stand" block at the top of `docs/PROGRESS.md` is the project's state file. Its fixed fields are: last updated, milestone, in flight, blocked, waiting on Rob, and next. Any session that changes plan state rewrites that block in place, adds a dated log line, and commits before ending. The navigator owns the block; the orchestrator updates it after each merged little rock. Start every session by reading it.

## Status values
`todo` → `ready` (deps met, criteria clear) → `in-progress` → `review` (PR open, awaiting Rob) → `done` (PR merged). Also `blocked` (say why) and `parked` (dropped from the plan; say why).

## Changing the plan
Plans change. Scale the paperwork to the size of the change:
- **Small** (tweak acceptance criteria, reorder little rocks, split a little rock): edit the spec and add a line to `docs/PROGRESS.md`.
- **Medium** (add or drop a little rock, swap a tool, park something): do the small steps, plus add a `docs/DECISIONS.md` entry. Dropped work gets status `parked`. Never delete it.
- **Big** (add or cut a big rock, change the north star or the portfolio-ready cut line): do the medium steps, plus update the big rocks table and sequencing in `docs/MASTER_PLAN.md`, and state the timeline impact (Rob-hours, and days left before the interview).

Rules:
- **In-flight work on a changed item:** the orchestrator either finishes the current little rock and stops, or abandons the branch unmerged. No half-merged work.
- **Superseded decisions** are marked `superseded` (pointing to the decision that replaces them). Never erase them.
- **Commit the doc changes** after every plan change.
- **The cut line is protected.** Adding anything above the cut line pushes something else below it, and the navigator says what.

## Stack (details and reasons in `docs/DECISIONS.md`; all `proposed` until Rob confirms)
- **App:** Next.js (App Router) in **TypeScript** (strict) at the repo root, pnpm, Tailwind + shadcn/ui, dnd-kit, Zod, Drizzle ORM + drizzle-kit migrations, node-postgres (`pg`) driver. Deployed on Vercel.
- **Database:** Postgres 16. Local: Docker Compose. Deployed: Neon via the Vercel integration. Schemas: `app` (seat planner), `workday` (mock HRIS, read-only to the app), `analytics` (dbt marts; dbt also writes `analytics_staging`, `analytics_intermediate`, `snapshots`).
- **Mock data:** deterministic TypeScript generator using `@faker-js/faker` with a fixed seed.
- **Analytics:** dbt-core + dbt-postgres in `analytics/`, managed with uv. MetricFlow semantic layer (`dbt-metricflow`).
- **Ingestion:** TypeScript script that validates and loads mock biweekly Workday custom-report CSVs into raw and current tables, behind a reader interface so an API reader can replace it.
- **Orchestration:** `pnpm pipeline` (Workday ingest → dbt build) plus a GitHub Actions workflow standing in for Airflow.
- **Quality:** ESLint + Prettier, `tsc --noEmit`, Vitest (unit and database tests), Playwright smoke tests, `dbt build` and `mf validate-configs` in CI.

## Commands (target; LR-01-02 onward creates them)
- `docker compose up -d db`: start local Postgres.
- `pnpm dev`: run the app at http://localhost:3000.
- `pnpm db:generate` / `pnpm db:migrate`: generate / apply Drizzle migrations.
- `pnpm db:seed`: wipe and reseed `app` + `workday` from the fixed seed. `pnpm db:seed:check` prints the seed checksum.
- `pnpm workday:ingest <file>`: validate and load one Workday report CSV (BR-03).
- `pnpm pipeline [--report <file>]`: ingest → `dbt build`, with a summary (BR-03).
- `cd analytics && uv run dbt build`: build and test all dbt models.
- `cd analytics && uv run mf query --metrics headcount --group-by metric_time__month`: query a metric (BR-06).

## Engineering conventions
- TypeScript `strict: true`; no `any` without a comment saying why. Node LTS pinned in `.nvmrc`; pnpm pinned in `package.json` `packageManager`. Python pinned in `analytics/.python-version`; dbt packages pinned in `analytics/uv.lock`. Pin each tool version in one place.
- **Server/client boundary:** anything that touches the database lives in `src/server/` (with `import "server-only"`) or in `scripts/`. Client components call server actions; they never import `pg`, Drizzle, or `src/server/`.
- **Mutations:** every mutation is a server action (or route handler) that (1) parses input with a Zod schema from `src/lib/schemas`, (2) derives the acting leader from the server-side cookie, never from input, (3) checks permission, (4) runs in one transaction, (5) returns a typed result `{ ok: true, ... } | { ok: false, code, message }`. Expected failures are results, not thrown errors.
- **Optimistic locking:** every `app.seats` update is `UPDATE ... WHERE seat_id = $1 AND version = $2` and sets `version = version + 1`; zero rows updated means a `CONFLICT` result and a rolled-back transaction.
- **Audit:** every seat change inserts into `app.seat_changes` in the same transaction. A move writes two rows sharing a `move_id`. Undo inserts reversing rows (`reverses_change_id`); nothing is updated or deleted.
- **Migrations:** schema changes go through `pnpm db:generate`; hand-written SQL (triggers, roles, grants) goes in a custom drizzle-kit migration. Never edit a merged migration.
- **Seed:** deterministic. Same seed → same checksum. Tests rely on named demo fixtures the seed guarantees (documented in `scripts/seed/README.md`), never on random row positions.
- **UI:** seat states are shown by label and icon, never color alone. Every drag interaction also has a keyboard "Move to…" path.
- **dbt layers:** `staging` (1:1 with sources: rename, cast, no joins) → `snapshots` (SCD2) → `intermediate` (joins, history logic) → `marts` (`dim_`, `fct_`, `rpt_`: what the app and metrics read). Marts read only intermediate, staging or other marts. Every model has a description and a YAML entry; every mart has `unique` + `not_null` on its grain (or `dbt_utils.unique_combination_of_columns` for composite grains); every enum column has `accepted_values`.
- **Explainers** (`docs/explainers/`) cite code as `path:line` and are updated in the same little rock that changes that code.
- Secrets only in `.env` / `.env.local` (gitignored), Vercel env vars, and GitHub secrets. Commit `.env.example`.
- Branch: `lr/LR-02-03-short-slug`; every commit message starts with the LR ID.
- **PR mode (on):** each verified and reviewed little rock becomes a GitHub PR titled with its LR ID, whose body carries the acceptance-criteria evidence and every reviewer finding with its disposition. Rob reviews and merges; agents never merge to `main`. A little rock is `review` while its PR is open and `done` once merged.

## Definition of done (every little rock)
1. Every acceptance criterion is met, with evidence (command + output, or test name).
2. Every applicable command under "Checks" passes locally, and CI is green on the PR.
3. Tests cover each new behavior and would fail on a plausible regression.
4. Docs touched by the change are updated (spec status, `docs/data-model.md`, explainers, README).
5. The reviewer found no P1; every P2 is fixed or waived with a reason in the PR.
6. Rob merged the PR.

## Project rules
The reviewer checks every one of these on every little rock. Add a rule when a decision creates
one, and cite the decision ID. Domain edge cases worth testing also go here.
- **Parameterized queries only.** No string-built SQL: use Drizzle's query builder or its `sql` tagged template with bound values. No `sql.raw()` with any value derived from input.
- **Every mutation is validated server-side**: a Zod schema plus a permission check of the acting leader against every squad the mutation touches (D-005, D-013).
- **Every seat update uses the optimistic-lock version check** and fails with `CONFLICT` on a stale version (D-011).
- **`app.seat_changes` is append-only.** No `UPDATE` or `DELETE` in code; a database trigger and grants enforce it too. Undo is a reversing insert (D-010).
- **The app never writes `workday` tables.** Only `scripts/ingest/` and `scripts/seed/` write them. Nothing under `src/` issues `INSERT`/`UPDATE`/`DELETE` against `workday`; from BR-07 on, the app's database role can't (D-015).
- **Ingestion validates the whole file before loading anything**, loads raw rows unchanged, and is idempotent by file hash (D-028). Cleaning happens in dbt staging, not in the loader.
- **Demo-only actions** (simulate another leader's edit, simulate Workday refresh, reset demo) sit behind `DEMO_MODE=true`, checked on the server, and return 404 otherwise (D-023).
- **No secrets or connection strings** in code, fixtures, docs, or CI logs. The one exception: the localhost-only Docker Compose defaults in `docker-compose.yml` and `.env.example`.
- **Mock data only.** The company is Second Republic Bank, a fictional bank whose name is a deliberate homage (D-001). The homage is the name only: no First Republic branding, logos, colors, products, org or team names, or internal terminology. Otherwise, no real company, employer, product, or person names anywhere: seed word lists, fixtures, tests, screenshots, or docs. Person names come from faker with the fixed seed. Never describe or imitate any real company's internal systems, and never mention the interviewing company.
- **dbt conventions** (above): right layer, description on every model, grain tests on every mart, `accepted_values` on enums.
- **Analytics reads are read-only.** The dashboard reads `analytics` marts with `SELECT`s only; dbt never writes `app` or `workday`.

### Domain edge cases
- A worker holds at most one seat at a time (no double-seating), including on every past date in history.
- Worker type must match seat type: employees fill employee seats, contingent workers fill contingent seats.
- Only `open` and `backfill` seats can receive a move; `offer_accepted` seats are reserved.
- A vacated seat becomes `backfill` (an approved seat to refill); seats are never deleted by a move.
- Workday worker status: `active`, `leave`, `terminated`. Only `active` workers can be moved. A worker on leave keeps their seat.
- Effective dates run from today to +90 days, with no backdating in v1 (D-012). Dates are calendar dates in UTC; quarter boundaries matter for plan checks.
- Moving seat to seat within one squad is allowed and still audited. Moving a worker to the seat they already hold is rejected.
- Division-scoped leaders can edit every squad below their division; group-scoped leaders only their group's squads. A move needs permission on both squads.
- Concurrent saves on the same seat: exactly one wins; the other gets `CONFLICT` and nothing is written.
- Undoing a change whose seats have changed since: `CONFLICT`. Undoing a change twice: rejected.
- A terminated worker who still holds a seat is a reconciliation exception, not a crash: the board still renders and flags it.
- Workday reports are messy on purpose: `Last, First` names, `MM/DD/YYYY` dates, status text (`Active`, `On Leave`, `Terminated`), worker type text (`Employee`, `Contingent Worker`), stray whitespace. Each report is a full extract: a worker missing from a later report is an exception, not a deletion.
- A rejected report file loads nothing and leaves the previous report as current.
- Headcount is a point-in-time measure: never sum daily snapshots across days. Contingent workers are excluded from `headcount` and included in `headcount_incl_contingent`.
